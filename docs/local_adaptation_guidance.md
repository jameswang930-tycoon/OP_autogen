# 本地定制硬件生态适配：架构演进指导

> 适用范围：在当前仓库单独拉出的本地适配分支上演进。
> 运行环境（客观约束）：OpenCode + GLM-4.7（上下文窗口 128K，理解与推理能力弱于 Opus 4.8）。远端硬件与仿真器细节属机密，本文不涉及、也不假设其内部实现。
> 术语约定：正文用中文；首次出现的英文术语在括号内注明含义；成对出现的对比术语（如 predict/measure、compute-bound/memory-bound）保留英文以免强译失真。

---

## 0. 一句话结论

这次转向的实质，不是"删掉几个 skill"，而是**流水线的因果方向反转**：从"先预测、再生成"（cost model 预测流水 → 生成）变成"先生成、再测量、再分析"（生成 kernel → 远端仿真实测流水 → 分析瓶颈 → 再生成）。cost model 从一个**预测器（predictor）**降级/转化为可选的**廉价预筛器（pre-screen）**，真实仿真成为**测量真值（ground truth）**。在这个新结构下，你对各 skill 去留的判断大方向正确，但需要更精确地重新划分（见 §1）。而由于本地是弱模型 + 小上下文，全篇的设计主线只有一句话：**把复杂度尽量移出 LLM、放进确定性工具（deterministic tooling）**（见 §7）。

## 1. 架构反转：重新划定各 skill 的去留

### 1.0 前置判断（已确认）：仿真器 functional + timing 兼具

**结论：已确认，删除 CPU 侧 emulator 的判断成立。**

术语先厘清：**functional simulator（功能仿真器）**会真实计算输出数值；**timing-only simulator（纯时序仿真器）**只建模"花多少时间、卡在哪"，不保证数值。二者正交——流水信息再精细也不蕴含数值正确。

实际情形：发射到远端仿真器的 Python 文件里**不止 kernel 本身，还带有比对数值的校验代码**。因此这套是**功能执行（真算数值）+ 时序反馈（流水）兼具**，而"比对"由脚本内的 reference（参考实现，numpy/torch 金标准）承担。

由此定论：

- CPU 侧 emulator 原本存在的唯一理由是"无真硬件时的正确性代理"，现在代理冗余 → **可以退役**，并顺带甩掉它 30–40% 的静默数值盲区。
- 但**正确性校验没有消失，只是被发射脚本吸收了**。原 `__init__.py` 四段式里的 kernel / reference / test 三段依然存在，只是执行位置从 CPU emulator 换成了远端仿真器。**这决定了 gen' 的产物形态**（见 §1.2 与 §7）。
- **正确性与性能必须是两个可分辨的信号**（见 §3.6），因为它们触发完全不同的循环分支。

### 1.1 新流水线（generate–measure–analyze 闭环）

```
[输入: NL / PyTorch / 固定 shape]
  → 生成 (gen'):  直接产出 Triton + extension kernel；首轮无实测反馈，依赖记忆(retrieved_experience)与启发式
  → 远端仿真 (sim): 执行 → 精细流水反馈 + (functional 时)输出 vs reference
  → 反馈适配器 (feedback-adapter, 确定性): 把海量流水反馈蒸馏成「7 段式摘要 + 机器可读 verdict」   [见 §3]
  → 瓶颈分析 (analyze): LLM 读 verdict 选优化杠杆；弱模型下"verdict→杠杆"尽量做成查表          [见 §3/§4]
  → 循环控制器 (loop-controller, 确定性): 按阈值判定是否停止 [见 §3]；否则把杠杆回喂给 gen'
  → 记忆写回 (memory writeback): 记录性能 + 沉淀经验                                          [见 §5]
[输出: 实测最优的 kernel]
```

### 1.2 与旧流水线的逐一映射（对你"去留判断"的精确化）

| 旧 skill | 旧职责 | 新命运 |
|---|---|---|
| **triton-plan** | 写抽象 7-engine DSL + 跑解析式模拟 → raw_llm | **职责反转**：写 DSL + 解析式模拟这部分**退役**（不再预测流水，改为实测）；但其"读流水数据 → 定位瓶颈 → 分类 → 给杠杆"的**分析逻辑保留**，迁移到"反馈适配器 + 分析"这一环，改由真实反馈驱动。建议在新分支上把它重构成一个 `sim-analyze` skill，不再叫 plan。 |
| **triton-gen** | 生成 emulator 形态 kernel（`from common import tl`） | **保留且成为核心**，但目标从 emulator 形态**改为真实 Triton + extension**。原正文里的"baseline triton → emulator 反向映射"整段删除；"NPU-compatible coding rules"改写成"extension 使用规则"（见 §4）。**产物形态：仍是多段式模块，不是裸 kernel**——因为发射到仿真器的文件必须自带 reference 与比对代码才能构成可发射的完整单元（见 §1.0）。即产出 kernel + reference + 比对/输出结构化结果三段。 |
| **triton-convert** | emulator kernel → 真实 triton（5 条机械改写） | **彻底退役**。gen 直接产出真实 Triton，无需转换。你的判断正确。 |
| **triton-verify** | CPU emulator 正确性校验（只读） | **CPU-emulator 版退役**；正确性校验**迁移**为"远端仿真输出 vs reference"（functional 情形下并入仿真调用）。不是"永不触发"，是换了执行者与位置。 |
| **triton-fix** | emulator 修复循环（≤5 轮） | **独立的 emulator-fix skill 退役**；但"仿真报正确性失败或性能回退时重新生成"这个**修复行为**保留，溶解进循环控制器的 re-generation 分支。 |

一句话：**convert 真死；plan 反转为 analyze；gen 保留并成为主力（换目标）；verify/fix 不是消失，而是溶进"仿真调用 + 循环控制器"。** 这样划分比"保留部分/永不触发"更贴合你后面在新分支上拆 skill 的实际需要。

### 1.3 关于删除 emulator 的一点保留意见

CPU 侧 emulator 作为正确性代理确实冗余（尤其它还有 30–40% 静默数值盲区）。但它曾提供一个仿真给不了的东西：**零仿真成本的本地快速检查**。在大 kernel 场景下仿真很贵（见 §2），保留一个**廉价的上仿真前置闸门（pre-sim gate）**——不是完整 emulate，而是"能否编译 / shape 与 dtype 是否自洽 / extension 调用是否合法"这种静态检查——可以在花掉一次昂贵仿真前挡掉明显坏掉的 kernel。建议：emulator 本体可以退役，但保留一个极轻量的静态 pre-sim gate。

## 2. 大 kernel 的迭代成本问题（你自己提出的核心风险）

你已识别到：每轮迭代 = 一次远端仿真；小 kernel 仿真快、无所谓，大 kernel 仿真慢、循环就贵。这是这套"实测驱动"架构的根本代价。四条正交的缓解手段，建议组合使用：

1. **减少迭代轮数（最有效）**：靠记忆（§5）提升首轮生成质量，让循环在更少轮内收敛。首轮 kernel 越接近最优，昂贵仿真调用越少。这是记忆模块在本架构中最硬的价值。
2. **降低单轮成本——代表性 shape 预探（proxy-shape probing）**：对大 kernel，先在一个**小的代表性 tile/shape** 上跑仿真，拿到流水特征（bottleneck 签名）后再把优化决策放大回大 shape。多数瓶颈判断（compute-bound 还是 memory-bound、是否欠填充）在小 shape 上已能定性。
3. **保留一个廉价预筛层（two-tier evaluation）**：不要把 cost model 完全删干净。把它降级成**本地、廉价、近似**的性能预估器，只用来在多个候选 kernel 里**预筛**，把昂贵的真实仿真只花在 top-1/top-2 候选上。真实仿真仍是最终信号。是否值得做这层，取决于仿真成本是否真的成为瓶颈——**建议先不做（直接全量真实仿真，简单且信号可靠），当大 kernel 仿真成本确实卡住迭代时再引入**（符合最小可用优先的原则）。
   - 注意：这层预筛若要面向本地硬件，需要用仿真数据**离线拟合**本地引擎的带宽/时延曲线（把仿真在一组 transfer size 上的实测点，拟合成 `SATURATION_PARAMS` 那种曲线）。这个拟合只用到"size→带宽/时延"这类聚合数字，**不触碰、不泄露机密硬件原语**，与你的 public/confidential 纪律相容。
4. **结果缓存（memoization）**：以 (op, shape, kernel 变体指纹) 为键缓存仿真结果，避免同一变体被重复仿真。循环里回退/振荡时尤其有用。

## 3. Q2 + Q3：仿真反馈的提炼、瓶颈分析方法、停止准则

这三者强耦合，一起说。

### 3.1 现有 bottleneck-analysis 方法评估（合理之处，先肯定）

现有方法（在 `costModel/cost_emulator/Skills/bottleneck-analysis/SKILL.md`）其实是**结构良好、值得保留其骨架**的：

- **critical-path-first（关键路径优先）**：只优化落在关键路径上的算子，路径外的再快也不缩短总时间。这是正确的分析次序。
- **把主导代价归入一个小而可操作的分类**：compute-bound（算力受限）/ saturated 的带宽受限（已达峰值带宽）/ below-peak 的传输（size 太小、未达峰值）。每一类**直接对应一个明确的优化杠杆（lever）**（批量化、拆 WAR 依赖、重叠、减少数据量）。这个"分类→杠杆"的映射是这套方法的精华。

**结论：分析方法本身合理，保留其骨架。** 需要改的不是方法论，是它的**输入来源**和**面向弱模型的封装形式**。

### 3.2 它的短板（针对本次转向）

7 段 raw_llm 是**解析式模型的产物**：`regime=floor/ramp/saturated`、`k0`、"7 个固定引擎的利用率"这些概念，都是那个抽象模型的语汇。真实仿真反馈的结构不同、粒度细得多（真实流水级、stall 类型、bank 冲突、指令级占用、各级存储流量……）。把这些原样丢给 GLM-4.7 会**撑爆上下文、且让弱模型无所适从**。

### 3.3 paraphrase 策略（Q2 的核心）

原则：**保留输出接口的"形状"（7 段式结构摘要），替换其来源与提取逻辑。** LLM 已经"会读"7 段格式，保留这个接口，gen 就不用重学。

做一个**确定性的反馈适配器（feedback-adapter）**，读原始仿真反馈，产出与旧 7 段同构的摘要。这与之前 Q2 谈的"`Op` 列表接缝 + render_llm"是同一招：适配器把仿真 trace 解析进统一的算子/阶段结构，再由一个 render 函数吐出熟悉的摘要。适配器在**确定性代码里**（不是 LLM）完成三件事：

1. **Reduce（削减）**：从上千条流水事件里，只留下真正决定决策的少数——关键路径 + top-k 主导代价。路径外的一切对决策都是噪声。
2. **Classify（归类）**：给每个主导代价打一个**固定小词表**里的类别标签。把旧的三分类适配成本地硬件真实的 stall 类型，但**保持类别集合小而固定**，以便"类别→杠杆"能做成查表。**这个词表必须稳定**（见 §5：fingerprint 以 bottleneck 为键，词表一漂移，检索命中率就崩）。
3. **Verdict（结论）**：在摘要顶部输出**一句话结论**"主瓶颈 X + 建议杠杆 Y"，让弱模型不必自己从长文里重新推导。详细分段作为备份。

两条工程约束：

- **限定 token 预算**：把 paraphrase 后的反馈**限制到固定小体量**（如只保留关键路径 + top-5 代价 + 一行 verdict）。GLM-4.7 的 128K 要同时装 extension 速查表（§4）、记忆（§5）、kernel 本身，反馈必须精简。
- **verdict 机器可读**：verdict 顶部附一个**小 JSON 头**（如 `{"bottleneck": "memory_underfilled", "lever": "bulk_copy", "metric_ns": 1234, "expected_gain": 0.3}`），让**确定性的循环控制器**（不是 LLM）来读瓶颈类别、判停、更新记忆 fingerprint。不要指望弱模型去解析它自己写的分析。

### 3.4 对分析方法本身的两点增强

- 给每条优化建议附一个**量化的预期收益（expected payoff / headroom）**（类似旧 `--nx` 的 `speedup_if_reduced`）。循环据此判断"这个杠杆值不值得再花一次昂贵仿真"，直接喂给 §3.5 的停止逻辑。
- verdict 机器可读（见上），使**判停、选杠杆、写记忆都能由确定性代码驱动**，把弱模型从"读长文做判断"里解放出来。

### 3.5 Q3：停止准则（现状 + 建议）

**现状（已核实）**：bottleneck-analysis 的 Step 4 只有**定性**停止条件——"makespan 不再明显改善，或关键路径已均衡，或剩余代价已达峰值不可约，且 --verify 仍 PASS"。**没有任何量化阈值、没有迭代上限。** 你的印象属实。对弱模型而言这是重灾区：GLM-4.7 判断"是否还值得继续"很不可靠，会么无限循环、么过早收手。

**性能主口径指标（已确认）：cycles（周期数）。** 由仿真器直接给出，不受墙钟时间、机器负载、批次波动影响，可复现、可比较。两点使用约定：

- **判停用归一化的相对改善**（相对 best-so-far 的百分比），不要用绝对 cycles 比。绝对值跨 shape 不可比，而记忆是按 `op_kind|bottleneck` 检索、会跨 shape 复用经验。
- **绝对 cycles 仍要存进 runlog**（把 `AttemptRecord.latency_us` 改名/并列为 `cycles`）。归一化用于决策，绝对值用于事后分析与跨轮对比。

**停止决策交给确定性的循环控制器（loop-controller）。结构上：边际收益阈值做主判据，轮数上限做兜底护栏——两者互补，不是二选一。**

> 为什么不能只用固定轮数：固定轮数与收益完全脱钩，两种坏情况都会发生——(a) 第 2 轮已收敛（改善 <1%）却仍要烧满 5 轮，对大 kernel 是纯浪费；(b) 第 5 轮仍在每轮改善 15%，却被硬停、掐掉明显还在爬坡的优化。

满足以下**任一**即停：

1. **边际收益阈值（主判据）**：本轮相对 best-so-far 的 cycles 改善 < ε（起点值 3–5%）→ 收益递减，正常收敛。**这应是多数情况下真正触发的那条。**
2. **轮数上限（兜底护栏）**：达到 N 轮（起点值 5–8）→ 防止无限循环，保证最坏情况有界。
3. **不可约**：瓶颈类别为 compute-bound-at-peak 或带宽已饱和且无适用杠杆（分析判定 irreducible）→ 停。
4. **无进展 / 振荡**：瓶颈类别连续 2 轮不变，或循环在两个变体间来回（以 kernel 变体指纹检测）→ 停。
5. **数值 FAIL 且重生成仍不过** → 停并上报。

**回退保护（regression guard）**：某轮优化后 cycles 反而变大 → **回滚到上一版**，可再试一个备选杠杆，仍无改善则停。

**best-so-far 底线**：全程保留历史最优变体，**停止时返回实测 cycles 最优的那一版，而不是最后一轮那一版**。这条极易漏，但没有它，一次末轮的失败优化就会盖掉前面全部成果。

**两条计算口径（容易出错，务必明确）**：

- **判停只在数值 PASS 的轮次上计算改善**——数值 FAIL 轮次的 cycles 无意义（算错的 kernel 快不快毫无意义），不参与"改善了多少"。
- **但 FAIL 轮次仍计入轮数预算**，否则一个反复算错的 kernel 会让循环永远不达上限。

**阈值标定**：ε 与 N 本质是成本/收益的权衡参数，取决于单次仿真多贵。**做成可配置参数，不要硬编码**。先按起点值跑几个真实算子，观察典型收敛曲线（一般前 2–3 轮改善大、之后迅速衰减），再回头校准。大 kernel 单次仿真贵 → ε 调高、N 调小（早停省预算）；小 kernel 仿真便宜 → 可放宽多探几轮。

关键架构点：**判停必须在确定性控制面里，读 §3.3 的机器可读 verdict，而不是靠 LLM 的散文判断。** 这既贴合你已锁定的"控制面与 LLM agent 分离"不变量，也正是对 GLM-4.7 弱判断力的补偿。

### 3.6 正确性与性能：两个必须可分辨的信号

发射脚本一次跑完会同时产出"数值对不对"与"流水多快"。循环控制器必须**分别**读到二者，因为它们触发完全不同的分支：

| 信号组合 | 控制器分支 |
|---|---|
| 数值 FAIL | 走**重新生成/修复**分支；**性能数据直接作废** |
| 数值 PASS + cycles 无改善 | 走**换优化杠杆**分支 |
| 数值 PASS + cycles 改善 | 记为 best-so-far，继续或判停 |

因此**发射脚本的输出必须是结构化的**，至少形如：

```json
{"correct": true, "max_abs_err": 1.2e-6, "cycles": 148230, "pipeline": {...}}
```

不要让 correctness 与 timing 混在一坨自由文本里等 GLM-4.7 去解析——与 §3.3 的 verdict 机器可读是同一个道理。

**成本提醒**：每次仿真都同时付出功能执行与时序采集的开销。因低级错误（shape 不匹配、语法问题、extension 调用非法）浪费一次大 kernel 仿真是最亏的，这反过来强化了 §1.3 的 **pre-sim gate** 建议。

## 4. Q4：把 extension 信息组织好喂给弱模型

目标 kernel = vanilla Triton（标准 Triton 语法）为主体 + 机密硬件 extension（类比 Triton-Ascend / torch-npu 那种"给算子工程师用的、支持特定硬件加速的接口"）。GLM-4.7 上下文小、理解弱，所以 extension 知识必须**精炼、可检索、按需加载**。

### 4.1 组织成"extension 速查表（cheatsheet）"，不是完整 API 手册

每个 extension 原语（primitive）只给最小必要信息：**名称 / 一句话语义 / 签名 / 何时用（针对哪个瓶颈类别）/ 一个最小规范示例 / 常见坑**。只收录会被实际用到的原语。

### 4.2 按"瓶颈类别"索引 extension 原语（最高杠杆的一招）

既然整个循环是瓶颈驱动的，就把 extension 原语**按它能解决的瓶颈类别编排**，例如：

- `memory_underfilled`（传输欠填充）→ extension 的 bulk / async-copy 类原语
- `compute_bound`（算力受限）→ extension 的专用 MAC / tensor 类原语
- `stall_dependency`（依赖 stall）→ extension 的双缓冲 / 流水重叠原语

这样弱模型能**从 §3.3 的 verdict 直接查到该用哪个原语**，不必理解整个 extension 全貌。这是让平庸模型正确用上 extension 的最有效方式，且与 §3、§5 的瓶颈词表共用同一套类别标签（务必保持一致）。

### 4.3 渐进披露（progressive disclosure），别整本塞进上下文

沿用你已经验证过的机制：把 extension 知识做成一个 **skill + references**——SKILL.md 正文放"vanilla Triton 生成规则 + 一张极短的原语清单（名称 + 所解决的瓶颈类别）"；每个原语的详细参考放 `references/`，**只在瓶颈类别命中该原语时按需读**。这样常驻上下文的只有一张短索引。

### 4.4 让 vanilla Triton 作为永远可回退的底座

指示 gen：**默认写标准 Triton，仅当某个瓶颈类别明确要求时才引入对应 extension 原语。** 好处是基线永远是合法 Triton，extension 是叠加的、局部的优化。这样即使弱模型没完全吃透 extension，最坏情况也是产出正确的 vanilla Triton，而非坏掉的代码。

### 4.5 机密切分（沿用现有纪律）

带真实原语语义的 extension 速查表放**机密的本地分支/环境**，不进公开仓。公开框架只定义**接口约定**："gen 从路径 X 读一张按瓶颈类别索引的 extension 速查表"；机密侧填内容。本文只规定速查表的**格式与约定**，内容由你在机密侧编写。

## 5. Q5：保留并演进记忆模块

强烈赞成保留。对 128K 的弱模型，**跨会话持久化的蒸馏记忆是整套架构里性价比最高的部件**——它把"经验"从易失的上下文里搬到持久存储，正面补偿小窗口。

### 5.1 好消息：现有结构对本次转向是稳健的，保留即可，不用重建

- **fingerprint（算子特征）键 = `op_kind | bottleneck`**，`shape_sig`（形状特征）为预留位、暂不进键。转向后 `bottleneck` 的**来源**从解析式模型换成真实仿真（经 §3 paraphrase），但**结构不变**。
- **retrieve（检索）/ writeback（写回）/ CLI（inject/record/add/stats）三套接口继续适用。** inject 在生成前把 retrieved_experience 追加进 .plan.json 供 gen 读，record 在校验后写日志并更新经验统计——这套 hook 位置在新循环里依然成立。

### 5.2 唯一必须改的关键点：价值信号从"正确性"转向"性能"

现状：`score() = (helped+1)/(used+2)`，其中 **helped = "该经验在场且这一次通过了正确性校验（passed=True）"**。也就是说，当前记忆奖励的是"与正确性通过相关"的经验。

转向后，正确性（在 functional 仿真下）基本是既定前提，**真正稀缺、值得记住的是"是否带来更快的 kernel"**。`AttemptRecord` 里已经有 `latency_us` 字段但没进 `score()`。演进方向：

- `record_attempt` 采集**仿真给出的 cycles**（§3.5 已定的主指标），不止 `passed:bool`；把 `AttemptRecord.latency_us` 改名/并列为 `cycles`。
- `score()` / `bump()` 的奖励信号改为**与性能改善相关**（例如：helped 重定义为"该经验在场且这一轮刷新了该 fingerprint 的历史最优 cycles"），而非仅正确性通过。
- **正确性作为前置闸门、性能作为排序信号**：`correct=false` 的尝试**不参与性能打分**，但**仍要写进 runlog**——失败经验同样有价值（哪些做法会导致数值错误，是值得记住的）。信号来源见 §3.6 的结构化输出。

### 5.3 冷启动价值（把记忆和大 kernel 成本问题接起来）

新循环里，**首轮 kernel 没有任何实测反馈**，只能靠 op 语义 + 启发式 + `retrieved_experience`。所以记忆直接**替代了缺失的首轮测量**：好的历史经验 → 更接近最优的首轮 kernel → 更少的昂贵仿真轮数。这既是记忆在本架构中最硬的价值，也是 §2"减少迭代轮数"的落地手段。请在设计里把这条显式化。

### 5.4 让经验携带 extension 原语（把 Q4 和 Q5 闭环）

给 `Experience` / `AttemptRecord` 加一个可选字段 `extension_used`。一条经验形如"op=matmul，bottleneck=memory_underfilled，用了 extension 原语 X，加速 2.1×"，就能让记忆**对复发的瓶颈直接推荐正确的 extension 调用**，把 §4 的"瓶颈类别→原语"和 §5 的历史经验接成闭环。

### 5.5 蒸馏策略：先模板化、后 LLM 蒸馏（针对弱模型）

现状 `add_experience` 是手工/模板；自动蒸馏是预留位（设想由离线蒸馏智能体读日志、提炼、去重、消解矛盾）。**别让 GLM-4.7 在线自由写经验**——弱模型会写出含糊甚至矛盾的经验，污染经验库。建议：

- **早期：结构化模板经验**。record 时按固定模板写入结构化事实（"op_kind=X，bottleneck=Y，lever/primitive=Z，speedup=S"）。可读、可去重、不易污染。
- **后期：离线蒸馏**。攒够日志后，用一个离线过程（可以是能力更强的模型，或人工）把日志蒸馏成自由文本经验。**在线循环里不做自由文本蒸馏。**

### 5.6 词表稳定性（与 §3、§4 的硬耦合）

因为 fingerprint 以 `bottleneck` 为键、extension 又按瓶颈类别索引，**§3.3 反馈适配器输出的瓶颈类别，必须来自一个固定、有限、跨模块统一的词表**。词表一漂移，fingerprint 键空间碎裂、检索命中率下降、extension 查表也失配。建议在新分支里把这个**瓶颈类别词表作为单一定义源（single source of truth）**，供 adapter / memory / extension-cheatsheet 三方共同引用。

## 6. Q1 贯穿全篇的设计原则：把复杂度移出 LLM

本地是弱模型 + 小上下文，这不是某一问的约束，而是**贯穿所有设计的第一原则**：**模型越弱，框架就越要用确定性脚手架把它围起来，越少依赖模型自身的判断与上下文。** 具体落到前面各节：

- 瓶颈的**提取、削减、归类、判停**——放确定性代码（§3），LLM 只读一行 verdict、只做"查表选杠杆 + 写 kernel"这类它能胜任的窄任务。
- 停止用**明确数值阈值**（§3.5），不用定性判断。
- extension 用**按瓶颈类别索引的短速查表 + 渐进披露**（§4），不把整本手册塞进上下文。
- 记忆用**持久化 + 结构化模板**（§5）补偿小窗口，不靠模型在线蒸馏。

一句话：给 GLM-4.7 的每一步，都应该是"读一个短的结构化输入 → 做一个窄决策 → 产出一个受约束的输出"，而不是"读一大坨 → 自己想清楚 → 自由发挥"。

## 7. 新分支落地清单

按你"单独拉分支演进"的计划，建议的动作与产物：

**skill 增删**
- 删：`triton-convert`（退役）。
- 改造 `triton-plan` → `sim-analyze`：去掉"写抽象 DSL + 解析式模拟"，保留"读（paraphrase 后的）真实反馈 → 定位瓶颈 → 出 verdict"。
- 改造 `triton-gen` → `triton-gen'`：目标改为真实 Triton + extension；删除 emulator 反向映射段；把 NPU-coding-rules 换成 extension 使用规则（按 §4）。
- `triton-verify` / `triton-fix`：**溶解进"发射脚本内的 reference 比对 + 循环控制器"**（§1.0 已确认为 functional）。注意 gen' 仍须生成 reference 与比对代码，这部分职责不消失、只是换了执行位置。
- 新增（确定性、非 skill）：`feedback-adapter`（§3.3）、`loop-controller`（§3.5）、`bottleneck 词表单一定义源`（§5.6）；可选 `pre-sim gate`（§1.3）与 `proxy-shape probing`（§2）。

**接口约定（务必显式化、单一来源）**
- 瓶颈类别词表：adapter / memory / extension-cheatsheet 共用（§5.6）。
- verdict 机器可读头（§3.3）：loop-controller 与 memory 据此判停、写回。
- extension 速查表格式（§4.5）：公开框架定义格式，机密侧填内容。
- `.plan.json`（或其后继）继续作为文件态单一交接物，延续"状态只走文件、不进会话"的不变量。

**机密切分（沿用现有纪律）**
- 公开框架：流水线骨架、adapter/controller 接口、memory 框架、瓶颈词表定义、extension 速查表**格式**。
- 机密本地：远端仿真适配、本地硬件校准数字、extension 速查表**内容**、真实硬件原语。

**验证方式（怎么确认新分支生效）**
1. 小 kernel（如 vadd）走通一轮完整闭环：gen' → 仿真 → adapter 出 7 段+verdict → controller 判停 → memory 写回，产物为实测最优 kernel。
2. 停止逻辑（现状缺失、最该验的一环），三个用例分别验：
   - **边际收益**：构造"每轮仅 1% 改善"的场景 → 应在 ε 处停，而非跑满 N 轮。
   - **回退保护 + best-so-far**：构造"第 3 轮 cycles 反而变大"的场景 → 应回滚，且最终返回的是**历史最优那版**，不是最后一轮那版。
   - **FAIL 计数口径**：构造"连续数值 FAIL"的场景 → 确认 FAIL 轮次不参与改善计算、但计入轮数预算（不会永不达上限）。
3. 记忆冷启动：清空经验库跑一遍、再带经验跑一遍同类 op，确认第二次首轮 kernel 更优、仿真轮数更少（§5.3 的价值验证）。
4. 词表一致性：确认 adapter 输出的 bottleneck 标签、memory fingerprint 的键、extension 速查表的索引，三者取自同一份词表（可写成一个静态检查，纳入之前提过的 pre-commit）。
