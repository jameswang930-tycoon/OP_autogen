# 项目完整交接文档 — Triton Agent Optimizer

> 生成: 2026-07-24 | 供接手的大模型快速理解整个项目。

---

## 1. 项目目标

构建一个 **LLM Agent 驱动的 Triton Kernel 自动优化框架**，目标硬件 **华为 Ascend 910B3 NPU**。

**核心差异化**: 不靠盲试（AutoKernel 300~400轮），而是通过 **DSL 流水线分析 (msprof op simulator + HIVMIR 编译器产物)** 精确诊断瓶颈——知道哪个 op、哪个引擎、带宽利用率多少、该改什么参数。预估 20~50 轮收敛。

## 2. 重要概念澄清

### msprof op simulator ≠ 真机 msprof

| | msprof op simulator | msprof op (真机) |
|---|---|---|
| 需要硬件 | ❌ 不需要 | ✅ 需要 NPU |
| 运行方式 | 纯 CPU 仿真，CANN Toolkit 即可 | 真机采集 |
| 输出 | trace.json (Chrome Trace Event Format) | OPPROF_xxx/ (CSV + JSON) |
| 用途 | 指令流水线分析 | 真实性能数据 |

**关键**: msprof op simulator 可以在 **Linux 无 NPU** 环境运行。安装 CANN Toolkit → `msprof op simulator ./binary` → 生成 trace.json。

### Cost Simulator ≠ msprof

`costModel/cost_emulator/simulator.py` 是合作方写的 Python 模拟器，输入是 DSL 字符串（`alloc(gm_1, 128KB) gm_to_ub(ub_1, gm_1)`），输出 `--llm` 格式文本。它用 SATURATION_PARAMS 计算带宽和时序。**精度有限** (Engine 3/4/5/6 是 PLACEHOLDER)，但格式与真实 msprof 分析完全对齐。

### 两层 Emulator

- `cost_emulator/simulator.py` — **性能预估** (分析层用)
- `emulators/common/__init__.py` — **正确性验证** (Verifier Stage 1)

两者完全不同，不要混淆。

### Agent = Python 骨架 + LLM 大脑

Agent 的 .py 文件是 **Prompt 编排器**，不是自己写决策逻辑。Python 管理信息流（构建上下文、调用 API、解析输出），LLM 做推理（理解瓶颈、生成计划、改代码）。

### 优化顺序为什么是 Algorithm→Fusion→Tile→Memory→Compute→Arch

改了算法 → 融合结构要重做。融合了新 op → tile 参数要重调。所以从结构影响最大的开始。详见 `docx/OPTIMIZATION_METHODOLOGY.md`。

### 回退机制不需要特殊实现

Coder 把优化代码写入 `round_N/kernel.py`。Verifier 验证失败 → Orchestrator 标记 REVERT → `self.current_kernel` 不变 → 下一轮从上一轮代码开始 → 自然回退。

### Stage 1 的 Emulator 调用约定

Triton kernel 中 `tl.load(x_ptr + offs, mask=mask)` 是 Triton 指针风格。CPU Emulator 需要 `tl.load(x_ptr, offs, mask=mask)`。`emulator_runner.py` 自动做正则转换。

## 4. 完整数据流

```
Kernel.py
  → msprof op simulator → trace.json → msprof_analyzer → pipeline_report.json
  → Ascend Compiler → .mlir → hivmir_analyzer → hivmir_report.json
  → dsl_merger (op_id 对齐) → merged_report.json (29 fields)
  → bottleneck_diagnoser + data_extractor → ~2KB 诊断数据
  → Planner (LLM: 诊断+Playbook+历史+经验→计划) → plan.md
  → Coder (LLM: 计划+代码→修改) → kernel.py + diff.patch
  → Verifier (CPU仿真→正确性 / 910B3→性能) → verification.json
  → RecordManager (KEEP/REVERT→trajectory.json→CONTINUE/STOP)
  → Finalize (optimized_kernel.py + trajectory_chart.png)
```

## 5. 每轮输出

**round0 (基准)**: kernel + benchmark + msprof/ + hivmir/ + merged/
**roundN (优化)**: 同上 + plan.md + diff.patch + optimization_record.json + verification.json

## 6. 关键设计决策

| 决策 | 选择 | 为什么 |
|---|---|---|
| 优化顺序 | Algorithm→Fusion→Tile→Memory→Compute→Arch | 结构影响从大到小 |
| 瓶颈诊断 | 脚本规则引擎 | 确定性分类，压缩到 ~2KB |
| 策略生成 | LLM (Planner) | 需要 Playbook+历史+代码上下文 |
| 代码修改 | LLM (Coder) | 语义理解 |
| 调度器 | Python 状态机 | 管循环，不做决策 |
| 决策/记录 | RecordManager | 集中管理 |
| 验证 | Python 脚本 (2阶段) | 确定性 |
| 记忆 | JSON 文件 + 3级键匹配 | 简单，不需要向量库 |

## 9. 容易误解的点

- **三阶段验证→两阶段**: 原来加了 simulator 作为验证步骤，后来明确 simulator 在分析层做瓶颈诊断，不在验证环节
- **执行层 = 只跑两个脚本**: emulator_runner (CPU验证) + hardware_runner (910B3性能)，不是复杂的处理逻辑
- **optimization_trajectory.json = 中枢**: Orchestrator 只调函数，RecordManager 做所有写操作
- **回退 = current_kernel 不变**: 不删文件，不改代码，下一轮自然从上一轮代码开始
- **每轮 analyzer 都重跑**: Round N 开始前分析当前 kernel（因为 Coder 上一轮改过了），但本地无 NPU 时 fallback 到 round0 数据
