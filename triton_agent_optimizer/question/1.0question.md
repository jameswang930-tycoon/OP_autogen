## 🔴 Critical — 影响核心链路正确性

### [ ] C01 — msprof trace 全轮共用一份预制数据，非 per-kernel/per-round

- **现象**: 运行日志中 13 轮全是 `512 instrs, 8 cores, 1484.0ns`，没有任何变化
- **根因**:
  - `orchestrator.py:229,232,439,444,450` — `prev_ns` 和 `abs_speedup` 多处 fallback 到硬编码 `1484.0`
  - `orchestrator.py:234-249` — 每轮 msprof 重采逻辑被 `try/except` 包裹，CMake 编译因时间戳问题（`Makefile has modification time X s in the future`）每次都失败
  - 失败后静默跳过，继续用 round0 的预制 trace
- **影响**: speedup 计算基于 per-pipe 时间映射推算，不是真实 per-round 测量数据。优化决策的基础不可靠。
- **涉及文件**:
  - `agents/orchestrator.py:229,232,234-249,439,444,450`
  - `analyzers/hivm_to_ascendc.py` — CMake 编译链路
  - `main.py:232` — 硬编码 fallback 路径 `/home/hjkc2/msprof_out2`

### [ ] C03 — bw_util > 100% 的数据对不齐 bug

- **现象**: 带宽利用率计算值超过 100%，物理上不可能
- **根因**: HIVM 逻辑 size（源码估算的 memref shape × dtype）和 msprof 物理指令实际搬运的 size 不对齐
- **影响**: 瓶颈诊断误判 — 明明没饱和被判为饱和，反之亦然。Planner 收到错误信号。
- **涉及文件**:
  - `analyzers/dsl_merger.py:185-218` — merge 阶段的 bw_util 计算
  - `analyzers/hivmir_analyzer.py` — 逻辑 size_kb 提取
  - `analyzers/msprof_analyzer.py:421-423` — 物理 size 字段目前写的是 TBD
- **文档引用**: README.md "当前限制" 表格第 2 行；SESSION_SUMMARY_2026-07-28.md 第 429 行

### [ ] C04 — Softmax/reduction kernel 数值验证无法检测精度错误

- **现象**: Emulator Stage1 对 reduction 类型 kernel 只做崩溃检查（不崩溃 = PASS）
- **根因**: `emulators/common/__init__.py` 的 reference 函数不精确；`main.py:63-69` 的 `_classify_kernel_type` 区分了 element_wise 和 reduction，但 verifier 对 reduction 降低了验证标准
- **影响**: 优化改了算法逻辑但数值变错（如 online softmax 边界条件），Stage1 不会报 FAIL，错误的 kernel 可能被 KEEP
- **涉及文件**:
  - `agents/verifier.py` — Stage1 验证逻辑
  - `execution/emulator_runner.py` — CPU 模拟执行
  - `emulators/common/__init__.py` — Triton API 的 numpy 实现

## 🟠 Major — 影响鲁棒性和 Agent 决策质量

### [ ] M01 — HardwareRunner.benchmark() 完全未实现

- **现象**: 整个 Stage2 真机路径不存在
- **根因**: `execution/hardware_runner.py:34-35` — 方法体直接 `return HardwareResult(success=False, error_message="Not yet implemented on 910B3")`
- **影响**: `msprof_mode="hardware"` 路径永远不可用。Tier 6 优化无法验证真实硬件效果。
- **涉及文件**: `execution/hardware_runner.py`

### [ ] M02 — Coder 改 0 行静默成功，无重试

- **现象**: 运行日志中 Round 3(`break_war_dependency`), 9(`optimize_vectorization`), 11/12/13(`adjust_grid_count`) 都显示 `→ 0 lines changed`
- **根因**: `orchestrator.py:197-217` — Coder 返回 `success=True` + `lines_changed=0` 时，Orchestrator 无检测逻辑，直接进入 Verifier
- **影响**: 浪费了 HIVM 重新生成 + msprof 重采 + 编译时间。这些无效轮次也污染了 trajectory 历史。
- **涉及文件**:
  - `agents/orchestrator.py:197-217` — 缺少 `lines_changed == 0` 检测
  - `agents/coder.py:284-286` — stub 模式直接返回原代码

### [ ] M03 — TBD 占位符串在数据流中传播

- **现象**: `"待补充"` 字符串出现在 pipeline_report.json / hivmir_report.json 的字段里，而非留空
- **根因**:
  - `hivmir_analyzer.py:38` — `TBD = "待补充"`
  - `hivmir_analyzer.py:94,131-133,279,387,545-550` — 13 个字段默认用 TBD
  - `msprof_analyzer.py:47,103,406,421-423` — 7 个字段默认用 TBD
  - `dsl_merger.py:32,185-218` — merge 时有检查但非关键路径的 TBD 仍会流入 merged_report
  - `hivmir_analyzer.py:640` — 有 `assert opd["instruction"] != TBD`，说明作者知道这是问题
- **影响**: 下游消费者（bottleneck_diagnoser, data_extractor）收到字符串 "待补充" 而非 float/int，导致类型错误或静默错误分类
- **涉及文件**:
  - `analyzers/hivmir_analyzer.py:38,94,131-133,279,387,545-550,640`
  - `analyzers/msprof_analyzer.py:47,103,406,421-423`
  - `analyzers/dsl_merger.py:32,185-218`

### [ ] M04 — 全项目 30+ 处裸 except Exception / 静默吞异常

- **现象**: 关键路径的错误被吞掉，看不到真正的失败原因
- **根因**: 代码审计发现 30+ 处 `except Exception: pass` 或 `except Exception as e: print(...)`，包括:
  - `orchestrator.py:248-249` — msprof 重采失败静默跳过
  - `orchestrator.py:314-315` — HIVM 生成失败静默跳过（后续用空 dict 跑完一个空轮次！）
  - `orchestrator.py:371-372,816-817,823-824,833-834` — 输出文件写入/图表生成失败静默跳过
  - `planner.py:114-115,131-132` — 经验检索失败双 `pass`
  - `coder.py:255-256` — 错误记忆检索失败 `pass`
  - `verifier.py:118-119,328-329` — emulator 执行失败 `pass`
  - `config.py:456-457,866-867` — NPU 检测失败 `pass`
  - `record_manager.py:344-345` — record 写入失败 `pass`
  - `bottleneck_diagnoser.py:64-65` — simulator 加载失败 `pass`
- **影响**: 真正的 bug 被系统性地隐藏，debug 极其困难。一个 HIVM 生成失败会导致整个优化轮次的 merged report 为空、诊断为 bottleneck_op_id=-1、Planner 拿到空数据。
- **涉及文件**: 全项目 12+ 文件

### [ ] M05 — _stub_plan() 返回 [STUB] 前缀伪策略

- **现象**: LLM API 不可用时，Planner 降级为硬编码启发式策略
- **根因**: `planner.py:316-345` — `_stub_plan()` 返回策略名带 `[STUB]` 前缀、target_speedup 固定 1.05
- **影响**: `[STUB]` 前缀被写进 trajectory.json 和 plan.md，污染历史记录。如果 stub 和真实 LLM 轮次混合，后续轮次 history prompt 信息错乱。
- **涉及文件**: `agents/planner.py:316-345`
