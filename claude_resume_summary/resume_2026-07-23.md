## 1. 项目总体目标

构建一个 **基于 Agent 的 Triton Kernel 自动优化框架**，针对 **华为 Ascend 910B3 NPU**。

### 核心闭环

```
Triton Kernel (.py)
  → HIVMIR 分析 (编译器中间产物: 变量名/依赖关系/数据大小)
  → msprof Simulator (时序模拟: 带宽利用率/引擎利用率/瓶颈识别)
  → DSL 流水线合并 (精确到每个 op 的时间占比/瓶颈类型)
  → Agent 智能体 (Planner→Coder→Verifier, 按 Playbook 精准优化)
  → CPU Emulator 验证 (秒级正确性检查, 不上板)
  → 910B3 真机实测 (最终性能验证)
  → 记录本轮结果 → 下一轮 → 直到收敛
```

### 关键差异化优势 (vs AutoKernel / GEAK / KernelAgent)

**我们的方案不是盲试。** AutoKernel 只能知道 "这个 kernel 占了 60% 时间"，然后盲目尝试各种优化。我们的方案通过 **DSL 流水线分析** 精确知道：
- 哪个 op 是瓶颈 (如 op2: ub_to_gm)
- 为什么慢 (带宽利用率 46%, 在 ramp 区, k0=10.72KB, 当前 tile=1KB)
- 怎么改 (合并小传输, tile > 10.72KB 进入饱和区)

**精准度比盲试高一个数量级, 预估 20~50 轮即可收敛 (vs AutoKernel 300~400 轮)。**

## 3. 基础知识 (对话中学到的)

### 3.1 HIVMIR (华为编译器中间产物)

- **全称**: Huawei Intermediate Virtual Machine IR
- **是什么**: AscendNPU-IR 编译栈的最底层 IR, 在生成机器码之前
- **提供什么信息**:
  - 变量名 (如 `ub_1`, `gm_2`, `l0_1`)
  - 数据大小 (精确到 KB, 如 `memref<128KB>`)
  - 操作类型 (gm_to_ub, vadd, matrixmul 等)
  - 依赖关系 (RAW / WAR / WAW)
  - 内存区域归属 (GM / UB / L1 / L0, 通过 buffer 名前缀判断)
- **怎么获取**: 在 910B3 服务器上编译 Triton kernel 时, 通过编译器 pass 插桩提取
  - 对接脚本: `fusion_pipeline/extract_hivmir_from_compiler.py`
- **格式**: MLIR 风格文本, 如:
  ```
  hivm.alloc %ub_1 : memref<128KB>
  hivm.gm_to_ub %ub_1, %gm_1 : memref<128KB>
  hivm.vadd %ub_2, %ub_1, 1.0
  hivm.ub_to_gm %gm_2, %ub_2 : memref<128KB>
  ```

### 3.2 msprof Op Simulator

- **是什么**: `costModel/cost_emulator/simulator.py`, 一个**静态时序模拟器**
- **不是真实硬件执行**, 而是根据 DSL 程序 + 硬件参数模型 (饱和度曲线) 来**模拟**执行时序
- **输入**: DSL 程序 (alloc + gm_to_ub + vadd + ub_to_gm + ...)
- **输出模式**:
  - 默认: 人类可读的 ASCII Gantt 图 + 表格
  - `--llm --critical-path`: 结构化文本 (7 个 section), 给 LLM 消费
  - `--nx`: NetworkX JSON 图 (可编程查询)
  - `--verify`: 内存容量正确性检查
- **核心原理** (5 步):
  1. 展开: for 循环 → flat 指令流
  2. 算时长: `duration_ns = size_kb × 1024 / bw(size)` (饱和度曲线)
  3. 依赖分析: RAW/WAW/WAR hazards (tile-aware)
  4. ASAP 调度: 7 引擎并行, 同引擎排队
  5. 瓶颈提取: `time_ratio` 最大的 op
- **饱和度曲线**: `bw = vpeak × size / (size + k0)`, clamped to `peak_clamp`
  - size ≤ k0/2 → floor (吃不满)
  - k0/2 ~ 2×k0 → ramp (线性爬升)
  - size ≥ 2×k0 → saturated (达到峰值)

### 3.3 DSL 程序

- **是什么**: 用 7 种 API 描述的"数据搬运+计算"程序
- **API 列表**:
  - `alloc(name, size)` — 声明 buffer 大小
  - `gm_to_ub(ub_dst, gm_src)` — GM→UB 传输 (engine 0)
  - `ub_to_gm(gm_dst, ub_src)` — UB→GM 传输 (engine 1)
  - `vadd(ub_dst, ub_src, scalar)` — 向量加法 (engine 2, VecUnit)
  - `gm_to_l1(l1_dst, gm_src)` — GM→L1 传输 (engine 3)
  - `l1_to_l0(l0_dst, l1_src)` — L1→L0 传输 (engine 4)
  - `matrixmul(l0_dst, l0_src_a, l0_src_b)` — 矩阵乘法 (engine 5, CubeUnit)
  - `l0_to_gm(gm_dst, l0_src)` — L0→GM 写回 (engine 6)
- **支持 for 循环**: `for m in range(0, 10, 1) { gm_to_ub(ub_1, gm_1 + m*1KB) }`
- **Two pipelines**:
  - Vector: GM→UB → VecUnit → UB→GM
  - Matrix: GM→L1 → L1→L0 → CubeUnit → L0→GM

### 3.5 两种 Pipeline

```
Vector Pipeline (逐元素算子: add/relu/softmax/rmsnorm):
  GM ──gm_to_ub──→ UB ──vadd/vmul/vexp──→ UB ──ub_to_gm──→ GM
  (engine 0)       (engine 2)             (engine 1)

Matrix Pipeline (矩阵算子: matmul/conv):
  GM ──gm_to_l1──→ L1 ──l1_to_l0──→ L0 ──matrixmul──→ L0 ──l0_to_gm──→ GM
  (engine 3)       (engine 4)        (engine 5)        (engine 6)
```

### 3.6 CPU Emulator 验证

- **位置**: `emulators/common/__init__.py`
- **作用**: 在 CPU 上用 NumPy 模拟 Triton kernel 执行, 验证正确性
- **验证内容**: 多 shape + 多 dtype + 边界条件 + 数值精度
- **速度**: 秒级 (不上板, 不上 GPU/NPU)
- **为什么需要**: 真机每次跑要几分钟, CPU 模拟秒级。在 CPU 验证通过后才上板
- **局限**: 只能验证正确性, 不能测量真实性能 (性能用 simulator 预估 + 真机实测)

### 3.7 Agent 实现模式 (2025 共识)

**Agent 的 Python 文件 = Prompt 编排器 + 执行框架。决策智能在 LLM 侧。**

```python
# 以 PlannerAgent 为例 (伪代码)
class PlannerAgent:
    def generate_round_plan(self, bottleneck, history):
        # 1. Python 做的事: 构建上下文
        context = self.context_manager.build(bottleneck, history)
        playbook = self._select_playbook_section(bottleneck.type)
        cases = self.experience_retriever.retrieve_similar(bottleneck)

        # 2. LLM 做的事: 推理 + 生成
        prompt = f"""
        {playbook}
        {context}
        {cases}
        请生成本轮优化计划 (JSON 格式):
        {{"strategy": "...", "target": "...", "change": "...", ...}}
        """
        response = llm.call(prompt)

        # 3. Python 做的事: 解析 + 执行
        plan = json.loads(response)
        write_file(f"round_{N}_plan.md", plan)
        return plan
```

**这不是纯代码逻辑——Planner 不做自己的优化决策算法。它把上下文拼好, 让 LLM 决定该怎么做。**

## 4. 关键设计决策

### 4.1 验证三阶段

```
Stage 1: CPU Emulator (秒级, 每轮必跑)
  → 正确性: 多 shape + 多 dtype + 边界条件 + 精度
  → PASS 才进入 Stage 2

Stage 2: Cost Simulator (秒级, Stage 1 PASS 后)
  → 性能预估: 瓶颈分析 + 引擎利用率 + 关键路径
  → 参考数据, 不强制 gate

Stage 3: 910B3 Hardware (分钟级, Stage 1 PASS 后)
  → 真实性能: 编译 + 基准测试 + msprof + HIVMIR
  → 最终决策依据
```

### 4.2 单轮优化流程

```
Round N:
  0. 上下文准备 (滑窗 + 检索 + Playbook 注入)
  1. 瓶颈重分析 (如有新数据)
  2. 生成本轮优化计划文档 (round_N_plan.md) ★ 先计划再执行
  3. 代码修改 (单文件, 最小化改动)
  4. CPU Emulator 验证 (FAIL → 重试最多3次)
  5. Cost Simulator 预估
  6. 910B3 真机验证
  7. 决策 (Keep: 加速比>1.01 / Revert)
  8. 记录本轮 (optimization_journal.jsonl)
  9. 检查停止条件
```

### 4.3 输出格式对齐

**最终优化报告 = simulator `--llm --critical-path` 的 7 个 section + HIVMIR 富化字段。**

原因是 `.plan.json` 的 `raw_llm` 字段已经是这个格式, 整个 `/triton-plan → triton-gen` 流水线依赖它。

### 4.4 按需数据提取 (DataExtractor)

复杂 kernel 的 DSL 流水线可能有 50~200 op。**全量数据不入 prompt**, 只在文件系统保存。根据当前瓶颈类型, DataExtractor 提取 ~10 行关键数据 + 注入对应的 1~2 个 Playbook 章节。

### 4.5 上下文管理 (三层)

```
热上下文 (最近5轮): 完整保留 (代码+diff+验证+决策)
温上下文 (6~15轮前): 摘要保留 (策略+加速比+瓶颈类型)
冷上下文 (16轮+): 仅关键数据点 (加速比, 瓶颈类型)
```

### 4.6 6 层优化策略 (Tier 1~6)

| Tier | 策略类别 | 触发条件 | 晋升规则 |
|---|---|---|---|
| 1 | Block Size & Launch | 初期, 带宽利用率低 | 连续3轮无改进→升级 |
| 2 | Memory Access & Coalescing | bw_util<70%, regime=ramp | 同上 |
| 3 | Operator Fusion | 存在 RAW 依赖链, WAR avoidable | 同上 |
| 4 | Compute Optimization | compute-bound, 已达峰值带宽 | 同上 |
| 5 | 910B3 Architecture | 以上都试过 | 同上 |
| 6 | Algorithmic Restructure | 最后手段 | 无改进→停止 |

### 4.7 停止条件 (7 条)

1. 连续 5 轮 Revert
2. 达到理论峰值 90%
3. 轮次预算耗尽 (默认 200 轮)
4. 时间预算耗尽 (默认 6 小时)
5. 达到目标加速比
6. 所有策略层级耗尽
7. 平台期检测 (最近 10 轮加速比波动 < 2%)

## 6. 新对话可能的 Gap

### Gap 1: "为什么不用 AutoKernel 的方案?"
AutoKernel 是盲试——它只知道 kernel 慢, 不知道 WHY。我们的方案通过 DSL 流水线分析, 精确知道瓶颈是哪个 op、哪个引擎、带宽利用率多少、为什么慢。精准度高一个数量级。但代价是前期要多跑 HIVMIR 提取 + simulator 分析。

### Gap 2: "simulator 和 msprof 是什么关系?"
Simulator 不是真正的 msprof。它是合作方写的一个**静态模拟器**, 用 DSL 程序 + 硬件参数模型来预估性能。msprof 是华为官方的 profiling 工具, 在真机上跑才能拿到真实数据。我们现在用的是 simulator (初步分析), 真机 msprof 数据在 Stage 3 才收集。

### Gap 3: "为什么 Agent 全是 .py 文件, 不是 AI?"
每个 .py 文件是一个 **Prompt 编排器**, 不是纯代码逻辑。它负责把正确的上下文 (瓶颈数据 + Playbook + 历史案例) 在正确的时刻喂给 LLM, 然后解析 LLM 的输出并执行。真正做推理和决策的是 LLM。详见 §3.7。

### Gap 4: "哪些参数是可靠的?"
只有 Engine 0/1/2 的 SATURATION_PARAMS 是实测的 (来自 perf_test)。Engine 3/4/5/6 全是 placeholder。UB=192KB (来自 bench) 比 simulator 里的 512KB 更可信。不要基于 placeholder 参数做精确优化决策。

### Gap 5: "HIVMIR 怎么提取?"
需要在 910B3 服务器上, 通过 Ascend 编译器编译 Triton kernel, 在编译过程中启用 MLIR pass 插桩来提取。脚本已有: `fusion_pipeline/extract_hivmir_from_compiler.py`。本地 Windows 环境无法提取 HIVMIR。

### Gap 6: "DSL 程序怎么从 kernel 生成?"
这是当前最大的 gap——目前没有一个自动化的 "Triton kernel → DSL 程序" 转换器。`/triton-plan` skill 做的事情是 NL/pytorch → DSL, 但它不是 kernel → DSL。这个转换逻辑需要在 `analyzers/msprof_analyzer.py` 中实现, 或复用 `/triton-plan` 的部分逻辑。

### Gap 7: "fusion_pipeline 的 complete_data_merge.py 能不能直接用?"
可以, 但它目前是一个独立的命令行脚本。需要把它的 `SimulatorOutputParser`, `HIVMIRParser`, `DataMerger` 类抽取出来, 作为 `analyzers/` 下的模块导入使用。不需要改代码, 只需要改调用方式。
