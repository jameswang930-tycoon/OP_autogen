## 1. planner.py 职责与函数清单

**职责**：Prompt 编排器 + LLM 调用。输入 = 当前 tier 筛选的诊断字段 + Playbook 路径 + 历史 + sweep 结论 + 手递 + 优秀案例 → 输出 `RoundPlan`（策略 + changes[] + 晋升决策 + 手递）。

### 数据结构
- `RoundPlan`（planner.py:42）：`round_num/tier/tier_name/strategy/target_speedup/specific_change/expected_impact/verification_method/plan_text/promote/promote_to(0=本层,<当前=回退,>当前=晋升)/promote_reason/promote_evidence/handoff`。**promote 必须带 evidence，否则调度器拒绝**

### 函数清单
| 函数 | 核心逻辑 |
|---|---|
| `PLAYBOOK_FILES` / `TIER_NAMES` | tier→文件名/名称映射 |
| `_load_playbook(tier, playbook_dir)` | CODING_GUIDE.md 前 **1500** 字符 + 本层 playbook 前 **3500** 字符拼接（★关键约束表放文件最前, 避免 18KB 全文拖慢 nga） |
| `_build_system_prompt` | 旧版 System Prompt（v4 实际已不用, system 只剩一行"先调用 skill"） |
| `_extract_kernel_section(code, max_chars=2500)` | 以真正 `def main():`/`if __name__` 为截断点（防头部注释误截） |
| `_extract_config_constants(kernel_code)` | 只扫 `@triton.jit` 之前的 config 区, 正则提取常量, 支持多变量行 `BLOCK_M, BLOCK_N, BLOCK_K = 64, 64, 32` |
| `_format_history(history)` | 按 tier 分组全量梗概——每层 `轮数/best/最近2轮: change→speedup[result]`, 附 `(预期X vs 实Y)`（D2 反思闭环）、`↩回退`（REVERT）、`err` 前 30 字符 |
| `PlannerAgent.__init__(playbook_dir, use_llm=True)` | |
| `PlannerAgent.generate_v4(...)` | 主入口（见下） |
| `PlannerAgent._stub_plan_v4(tier, kernel_code)` | stub 也输出 changes[]；从 config 正则提取真实 BLOCK 行（含独立行 `BLOCK_K = 32` 兜底） |

### generate_v4 的 user prompt 结构（步骤 1-8 + 内联 + 任务 0-8 + JSON 示例）
1. 调 skill：`skills/triton-op-planner/SKILL.md`
2. 读 playbook（速查卡→情况A~J；★promote/结构层判断前必读文末"结构层优化执行教学"：有矩阵必须有 tl.dot、因果 attention 必须 kv_hi 剪枝、归约单遍，缺任何一项先做结构层不许 promote）
3. 读当前单文件（★current_kernel=最新被采纳版, 非源文件；重点 ② kernel 区）
4. 读诊断字段文件 `07_tier{N}_fields/tier{N}_fields.txt`（读不到用内联）
5. ★读完整数据上下文 `planner_context.json`（比 07 字段更全）
5b. ★官方实测优先：`traffic_kb/bw_usage_rate/active_bw` 优先于估算；Tier4 看 `roofline.traffic_redundancy_read >1.5=重复搬运`；`task.transfers` 的 bw 是估算只在无实测时用
6. ★读优化轨迹 `optimization_trajectory.json`（防重复/防误跳/防死循环回退）
7. 手递（JSON 截 600 字符, 作为部分参考仍独立判断）
8. ★本层优秀案例（`memory/tier{N}_cases.json`, 读失败→空文本不阻断）

内联数据：`extracted[:1600]` + config 常量 + history + 融合分析（仅 Tier2, 截 600）。

**任务 0-8**：①每轮精准原则（只出 1~2 个最有把握 changes, 改准优先于改多）②前层优先检查（算力低→Tier1, 多 kernel 串行→Tier2, 有→promote 回前层；trajectory 查前层已试过就别反复回跳）③瓶颈归属判断 ④changes 只允许当前 tier 策略（Tier3 禁改 DTYPE/算法/融合）⑤old_code 必须与当前 kernel_op.py 逐字符相同（从文件逐字复制）⑥只改单文件、不引入 num_warps/num_stages ⑦目标加速比 1.05~1.5x ⑧严格晋升必须 promote_evidence ⑨跳转填 handoff 格式。输出两遍 JSON 格式（真实示例 + 格式说明）。

**LLM 调用**：`LLMClient`（api/cli/stub 三模式）+ `extract_json` 容错解析（去 markdown 块、找首尾花括号、3 轮裸值加引号修复）；异常→fallback `_stub_plan_v4`。防御性解析 `_safe_float/_safe_int`（处理 `"1.1x"`/`"tier 2"` 后缀）。

## 2. Amdahl 编排（scheduler.py `_plan` :929-953）

每轮计算每个 kernel 的端到端占比：`_dtot = task_duration_us × launch_count`（★必须乘 launch, 否则 attention 复用 kernel 占比被低估 3×），`_pct = _dtot / total_us × 100`（total_ns/1000, 同源口径）。

多 kernel（>1）时降序排成 `A (60.0%) → B (30.0%)` 链，生成固定文本块：
```
# ══ Amdahl 优化优先级 (端到端收益 ≈ 占比×加速比, 先打占比最大的 kernel) ══
A (60.0%) → B (30.0%) → ...
★本轮优先优化占比最大的 kernel「X」; 动其他 kernel 必须给出理由 (如跨 kernel 融合/消除重复搬运).
```
**前缀插入** extracted（planner 第一眼看到）。任何异常静默跳过。

## 3. Tier 机制与轮次分配（6 层策略）

| Tier | 中文名 | 字段数 | 允许改动 | 禁止改动 | 特有步骤 |
|---|---|---|---|---|---|
| 1 | 算法结构 | 13 | 算法/结构 | — | round1 sweep |
| 2 | 算子融合 | 8 | 融合 | DTYPE/算法 | `_run_fusion`→08_fusion/ |
| 3 | 分块配置 | 8 | BLOCK | DTYPE/算法/融合 | 每轮 sweep |
| 4 | 访存 | 12 | 访存模式 | — | — |
| 5 | 计算占用 | 8 | 计算排布 | — | — |
| 6 | 910B3 架构 | 9 | 架构专属 | — | — |

每轮还有 `GLOBAL_FIELDS`（3 个前层信号）+ `TIER_PER_KERNEL`（每 kernel 一行概览）。

**无固定"每层 N 轮"表——事件驱动状态机（`_decide_tier` :1320）**：

| 触发条件 | 动作 |
|---|---|
| planner `promote=true` 且 evidence/reason 非空（严格晋升） | 跳到 `promote_to`（允许回退前层）；写 `10_tier_handoff.json` + `st["handoff"]`，记录 `tier_jumps` |
| promote 无 evidence | 拒绝, 本层转正常优化轮（前置门 :1804, 避免轮次白耗+budget 照涨） |
| 本 tier 连续 ≥3 轮无改进（`no_improve`：尾部同 tier 中 `speedup ≤ prev×KEEP_FLOOR(1.01)`；采集失败轮不计） | 前向晋升 tier+1 |
| 同跳转路径 `tier->target` ≥3 次 | 拒绝防死循环, 改前向晋升（Tier6 则停） |
| Tier6 连续 3 轮无改进 | 停止；Tier6 有改进→继续（B1 修复: 原来一轮即停是 bug） |
| 达到 target_speedup | 不硬停（D3）, `target=-1` 继续探后续层 |

- 轮次编号 rn 全局递增不随 tier 重置；promote 轮免费（`while (total_rounds - promote_budget) < max_rounds`，修复"两侧同步增长导致 max_rounds 失效、5 轮跑出 18 轮"）
- 每轮目录 `outputs/<op>/01_algorithmic_structure/roundN/`
- 手递由调度器消费一次即置 None（防重复引用）

## 4. sweep 流程与 prompt 注入

触发：`rn==1 或 tier==3` 且 `TIER3_SWEEP=1`（默认）。`_tier3_sweep_data`（:1136）在 **best_kernel.py**（非 current, 防噪声污染）上跑 `sweep_blocks.sweep`——程序化枚举全部 L0 合法 2 幂 BLOCK 候选, torch.npu.Event 单进程实测；最优写回 `round_dir/kernel_op.py` 副本并把 `current_kernel` 指向它（修复"写回 input 源文件破坏基准"）。结果持久化 `st["last_sweep_result"]`（只存结论：best/vars/n_configs/result_path/written/from_round, 防 trajectory 膨胀）。

prompt 注入（`_plan` :964-996）：`sweep_status` ∈ `ran_this_round / failed / skipped_no_free_params / not_triggered / reused_from_cache`。追加块 = 状态 + 来源（★本轮实测 vs `缓存 (R{n} 实测, 可能过期)`, `fresh` 标记 = 本轮新扫, B1 防"缓存当已穷举最优"误导 planner 禁调分块）+ 最优 BLOCK + 是否已写入 + 候选数/路径。

| sweep_status | planner 收到的指令 |
|---|---|
| tier3 且 fresh | "已穷举全部 L0 合法候选, 禁止猜新 BLOCK, promote 到下一层" |
| 缓存 | "只作参考, 结构已变可自行评估, 可触发新 sweep" |
| 非 tier3 | "BLOCK 已由 sweep 实测优化, 禁止再调分块（除非 msprof 发现新瓶颈）" |
| failed/not_triggered | "可自由调整" |

同时进 `planner_context.json` 的 `tier3_sweep` 字段和 history（sweep_ran/sweep_adopted/sweep_status）。B3：加速比相对当前块算（speedup_vs_cur）, 跨结构轮次不用旧 baseline。

## 5. 失败案例库注入（进 coder 修复器, 不进 planner prompt）

注入对象是 **coder 修复器**而非 planner prompt（scheduler `_code` 循环 :1842/:1952, code/verify 失败都经 `build_retry_context`）。按 tier 分文件 `memory/tier{N}_failed_cases.json`。

- `normalize_error`：800 字符、去 0x 地址/行号/路径/纯数字、英文词(≥4 字母去停用词)+中文片段→关键词→sha1 12 位指纹
- `classify_error` 四分类 env/code_compile/code_numeric/code_runtime（env 不入库）
- `retrieve` 两级：L1 指纹精确(+100 且计 hit_count) + L2 关键词交集≥2(每个×10)，+同 op(+5)+solved(+3)，取 ≤3 条，`fallback_all` 跨 tier 兜底
- `build_retry_context` 拼 ① 前几次(方案+报错)全序列 ② 本次报错 ③ 检索注入 `format_for_coder`（solved 给 solution/fix_diff、stuck 标"★此路不通 禁止原样重试"、open 可换新方案）④ 禁止原样重试提示
- ★先检索再入库（防首犯自命中）；负正闭环：方案曾在优秀案例成功→提示上下文差异
- 成功轮 `mark_solved` 回填。生命周期 open→attempts≥STUCK_AFTER(3)→stuck；solved 后再现降级 open。上限 50/层 LRU 淘汰

## 8. 已知坑与审查发现

4. rebaseline 环境漂移防护（每 10 轮, 同步重置 best Event, 不重置会永远 REVERT）
