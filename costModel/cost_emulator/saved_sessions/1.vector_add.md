● The optimal program is an element-wise scalar add: load 128KB from global memory, add 2.0, store back. The three ops map cleanly
  onto Triton's model — gm_to_ub is tl.load (DRAM→SRAM), vadd is the compute, ub_to_gm is tl.store (SRAM→DRAM).

  import torch
  import triton
  import triton.language as tl


  @triton.jit
  def add_scalar_kernel(
      x_ptr,            # gm_1: input in global memory
      out_ptr,          # gm_2: output in global memory
      n_elements,       # number of elements (128KB / dtype size)
      scalar,           # the 2.0 added by vadd
      BLOCK_SIZE: tl.constexpr,
  ):
      # One program instance handles one BLOCK_SIZE-wide tile.
      pid = tl.program_id(axis=0)
      offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
      mask = offsets < n_elements

      x = tl.load(x_ptr + offsets, mask=mask)   # gm_to_ub: GM -> on-chip (UB-equivalent)
      y = x + scalar                            # vadd: compute on the loaded tile
      tl.store(out_ptr + offsets, y, mask=mask) # ub_to_gm: on-chip -> GM


  def add_scalar(x: torch.Tensor, scalar: float = 2.0) -> torch.Tensor:
      out = torch.empty_like(x)
      n_elements = x.numel()
      # Single 128KB tile, matching the emulator's one-shot transfer.
      # 128 KB of fp32 = 32768 elements.
      BLOCK_SIZE = triton.next_power_of_2(n_elements)
      grid = (triton.cdiv(n_elements, BLOCK_SIZE),)
      add_scalar_kernel[grid](x, out, n_elements, scalar, BLOCK_SIZE=BLOCK_SIZE)
      return out


  if __name__ == "__main__":
      # 128 KB of fp32 == 32768 elements (the emulator's 128KB buffer).
      x = torch.arange(32768, dtype=torch.float32, device="cuda")
      out = add_scalar(x, 2.0)
      torch.testing.assert_close(out, x + 2.0)
      print("ok")

  A few notes on the mapping:

  - One tile, no splitting. The emulator analysis showed that splitting the 128KB into smaller tiles only multiplied the fixed
  transfer latency (the 2-tile version went 9→13 cycles). The Triton equivalent is keeping a single tile — BLOCK_SIZE =
  next_power_of_2(n_elements) gives one program instance covering the whole buffer, mirroring the single gm_to_ub/ub_to_gm pair
  rather than fragmenting it.
  - The RAW chain is implicit. In Triton you don't write the load→compute→store dependency explicitly; x = tl.load(...), y = x +
  scalar, tl.store(..., y) is the chain. The compiler keeps x and y in registers/shared memory (the UB-equivalent), so the data
  never round-trips through global memory between ops — same as ub_1/ub_2 staying on-chip in the emulator.
  - Size assumption. 128KB maps to 32768 fp32 elements (or 65536 fp16). If your buffer is a different dtype, only the element count
  changes; the kernel is unchanged.

  One caveat the emulator doesn't capture: on a real GPU a single-block kernel uses just one SM, so for large tensors you'd
  normally want a fixed BLOCK_SIZE (e.g. 1024) and let the grid span many blocks to saturate the device. I kept it single-tile here
  to stay faithful to the optimal emulator program; say the word if you'd rather have the throughput-oriented multi-block version.
